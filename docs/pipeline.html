Pipeline

From a Folder of Files to a Trustworthy Database

Every dataset in this project starts life as a file that someone else designed for their own purposes: an NDEP regulatory CSV, a field spreadsheet, a raw export from a temperature or conductivity logger, a scanned NDWR well-completion PDF. None of those formats agree with each other, and none of them were built with database integration in mind. The pipeline’s job is to take that pile of heterogeneous files and turn it into a single, internally consistent database that can be trusted for analysis, without ever touching or reinterpreting the original files themselves. It does that through five stages applied uniformly to every source: each file is first parsed and standardized into a common shape, then checked for structural and logical consistency, normalized into the shared relational schema, inserted into the database, and finally exported into the GIS, modeling, and web formats that downstream analysis actually uses. Because that sequence is identical for every source, a new data type — a new well-log batch, a newly digitized shapefile — is a matter of writing one more script that plugs into the same five stages, not redesigning the system.

Conceptual data flow: raw sources on the left feed dedicated ingestion scripts, which populate a normalized relational schema; derived products, quality control, and GIS/modeling exports all sit downstream of that shared core.

Reading the diagram from left to right tells the whole story: raw inputs enter through source-specific ingestion scripts that handle each format’s own quirks, land in a small set of core relational tables — Locations, Sampling Events, Samples, and the observation tables hanging off them — that everything else is built from, and then flow through a cross-cutting quality-control layer before being exported to GIS, the website, and eventually the geochemical and spatial modeling this project is building toward. That QC layer never modifies the underlying data; it only evaluates it and logs what it finds, which keeps the audit trail between a raw file and a database row completely unbroken.

Two Modes, One Codebase

The same pipeline code runs in two different modes depending on the situation. DEMO mode rebuilds the database from scratch on every run, which makes it deterministic and ideal for teaching, debugging, and proving that the whole system really can be reconstructed from raw inputs alone. OPERATIONAL mode instead persists the database between runs and grows it incrementally as new field seasons, lab batches, and temperature- and conductivity-logger downloads arrive — the mode this project actually runs in day to day. Because ingestion is idempotent by design (records are matched against stable identifiers like a temperature or conductivity logger’s serial number and timestamp, or a sample’s external ID, rather than blindly appended), running the same ingestion step twice, or leaving old files sitting in a raw-data folder, never duplicates or corrupts what is already there. A single configuration block at the top of run_pipeline.R decides which sources actually run on a given pass, so a targeted update — say, just the newest NDWR well logs — never has to pay the cost of re-processing everything else.

What the Pipeline Actually Has to Deal With

In practice, most of the engineering effort goes into handling the ways real-world environmental data misbehaves: file formats that vary release to release, column names that drift between one field season’s spreadsheet and the next, timestamps recorded in at least three different conventions depending on the source, coordinate systems that need reprojecting before anything can be mapped together, and the occasional literal duplicate record that has to be caught before it inflates a summary statistic. Temperature and conductivity logger ingestion is a good example of all of this at once: each deployment can arrive as a slightly different Excel export, with its own timestamp formatting and its own column layout, and the ingestion script has to normalize all of that into one consistent shape before a single row reaches the database. Solving that class of problem once, carefully, is what lets every later step — the QC checks, the GIS export, the eventual geochemical models — assume clean, consistent data rather than re-solving the same formatting problems over and over.

Once ingestion and validation are complete, a final post-processing stage updates spatial geometry for every location and well, rebuilds the GIS-ready views the GeoPackage export depends on, and reruns the full suite of quality-control checks across the database. The result is a set of outputs — a GeoPackage ready to drop into ArcGIS, a rendered website, and validated tables ready for the next stage of modeling — that are always freshly regenerated from whatever is currently in the database, and never hand-maintained separately from it.
