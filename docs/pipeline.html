pipeline

Overview

The pipeline implements a structured workflow that transforms heterogeneous environmental observations into a unified, reproducible analytical system.

Rather than treating ingestion, validation, and analysis as separate tasks, the system enforces a strict sequence of operations that ensures all data are consistently processed and comparable across sources.

The workflow consists of five primary stages:

  1. Ingestion — raw datasets are parsed and standardized
  2. Validation — structural and logical consistency checks are applied
  3. Transformation — data are normalized and relationships are defined
  4. Storage — observations are inserted into a relational database
  5. Export — derived products are prepared for GIS, modeling, and web use

This staged design ensures that all outputs are reproducible and traceable to their original inputs.

System Architecture

The system architecture is designed to integrate multiple observational domains into a single relational framework. Each component of the pipeline serves a specific role, but all are coordinated through a controlled sequence of transformations.

At the highest level, the system converts raw environmental observations into validated, structured datasets that support analysis, spatial interpretation, and modeling.

Key architectural principles include:

  • separation of raw data and derived products
  • normalization of all inputs into a shared schema
  • reproducible transformation through deterministic scripts
  • modular design allowing independent execution of components

Interpreting the Architecture

The diagram illustrates how heterogeneous data streams are unified through a common relational structure.

Raw inputs (e.g., NDEP datasets, field measurements, logger data) are first processed through dedicated ingestion pipelines. These pipelines handle parsing, validation, and normalization before inserting data into core relational tables.

The central tables—Locations, Sampling Events, Samples, and Observations—form the backbone of the system. All data types are linked through shared spatial and temporal keys, enabling integration across domains.

Derived datasets, such as hydraulic gradients, are computed from these core tables, allowing higher-level interpretation of system behavior.

Quality control operates as a cross-cutting layer, evaluating all datasets without modifying the underlying data. This ensures transparency while preserving the integrity of observations.

Finally, validated data are exported into multiple formats, including GIS layers, website outputs, and model inputs.

This architecture allows the system to scale from raw observation to process-based interpretation. ``

Execution Modes

The pipeline supports two modes of operation, designed to balance reproducibility with real-world data management.

DEMO Mode

In demonstration mode, the database is rebuilt from scratch on each run. This ensures deterministic outputs and allows the full system to be reproduced from raw inputs.

This mode is particularly useful for:

  • teaching and demonstration
  • debugging ingestion pipelines
  • validating end-to-end reproducibility

OPERATIONAL Mode

In operational mode, the database persists between runs and is updated incrementally as new data are ingested.

This mode reflects real-world use, where:

  • field data are added over time
  • laboratory results are incorporated as they become available
  • system evolution is recorded continuously

The distinction between these modes allows the same pipeline to support both reproducible research and active data collection workflows.

Pipeline Implementation (Simplified)

The pipeline is orchestrated through a central script (run_pipeline.R) that coordinates all stages of ingestion, processing, validation, and export.

Each ingestion module corresponds to a specific data source and can be enabled or disabled independently, allowing flexible execution depending on available datasets.

Example: Temperature Logger Ingestion

Temperature loggers provide high-frequency observations that require specialized handling during ingestion.

The ingestion process:

  • parses raw Excel exports
  • extracts timestamped temperature records
  • validates and standardizes time formats
  • links observations to spatial locations
  • inserts data into the relational schema

This process addresses several challenges:

  • inconsistent file formats across deployments
  • varying column structures
  • timestamp formatting differences
  • sensor-specific output variations

Successfully standardizing these datasets enables continuous monitoring to be integrated with discrete observations.

Challenges Addressed

The pipeline resolves several challenges common in environmental data systems:

  • heterogeneous file formats (CSV, Excel, sensor exports)
  • inconsistent naming conventions across data sources
  • temporal misalignment between datasets
  • spatial inconsistencies in coordinate systems
  • duplicate or conflicting records

By addressing these issues through controlled ingestion and validation, the system ensures that all datasets are compatible and comparable.

This provides a stable foundation for downstream analysis and interpretation.

Post-processing and Outputs

Following ingestion, the system performs a series of post-processing steps to prepare data for analysis and visualization.

These include:

  • updating spatial geometry for all observations
  • constructing GIS-ready views
  • generating GeoPackage outputs for spatial analysis
  • executing quality control checks across all datasets

These steps ensure that the database is not only internally consistent, but also directly usable in external tools such as GIS platforms and modeling software.

Post-processing transforms structured data into interpretable products.
