# Plan: Leapfrog data completeness, Facies_Clusters build, historic-figure library, PHREEQC/stats/potentiometric write-ups

Covers the large multi-part request: well-log/lithology/directional-data
audit for Leapfrog, a persisted `Facies_Clusters` table + GeoPackage

## Phase 1 — Persisted `Facies_Clusters` table + GeoPackage layer

- New additive schema `database/schema/13_facies_clusters_schema.R`:
  - `Facies_Cluster_Runs` (run_id, run_date, method e.g. `"ward_hierarchical"`,
    k, silhouette_width, mclust_agreement_pct, n_samples_clustered,
    core_analytes, notes) — one row per time `run_facies_clustering()`
    is executed and persisted, so a run's *method metadata* is never
    lost the way it currently is (console-message-only today).
  - `Facies_Cluster_Assignments` (run_id, sample_id, location_id,
    facies_cluster, facies_cluster_mclust) — one row per clustered
    sample per run; `UNIQUE(run_id, sample_id)`.
- New `scripts/analysis/register_facies_clusters.R` /
  `register_facies_clusters(con, facies_result)` — takes the existing
  `run_facies_clustering(con)` output (unchanged), inserts a new
  `Facies_Cluster_Runs` row and its `Facies_Cluster_Assignments` rows.
  Every call creates a **new** run (never overwrites a prior one) so
  re-running after new chemistry arrives keeps history, consistent
  with `PHREEQC_Solutions`-style versioning already used elsewhere.
- New `vw_facies_clusters_gis` view (latest run only, joined to
  `Locations` for coordinates) in `create_analysis_views.R`.
- New `facies_clusters` layer in `export_geopackage.R`, same
  `safe_write_layer()` pattern as every other point layer — this is
  the concrete "overlay clustering against digitized faults" ask;
  faults themselves stay empty until the user finishes ArcGIS
  digitizing (already scoped, unchanged).
- Wire into `run_pipeline.R` as its own `RUN_ANALYSIS$facies_clusters`
  stage (default `FALSE`, opt-in — like PHREEQC, this doesn't
  auto-run on every pipeline execution since clustering choices are
  meant to be reviewed, not silently regenerated).
- Verify against a scratch copy of `geochem_operational.sqlite` before
  applying to the real database (standard project convention).

## Phase 7 — Potentiometric-surface-mapping feasibility + software recommendation (write-up, no build)

Add a section answering the direct questions honestly, using the
real coverage numbers already gathered above:

- **Data sufficiency: not yet, for the field itself.** 2-3 wells with
  usable continuous water level inside the Steamboat field bounding
  box is far short of what any interpolation method needs for a
  defensible surface; the regional 21-well South Truckee Meadows
  network has real density but is largely a different hydrogeologic
  system. State plainly that the concrete blocker is the still-
  unanswered NDEP data request (Session 4) for water levels at the
  actual CPI/SB GEO production/injection/monitor wells.
- **Software recommendation, conditional on that data existing**:
  ArcGIS Pro Geostatistical Analyst (Empirical Bayesian Kriging) as
  primary, since this project's GIS workflow already targets ArcGIS
  and the `chloride_points` GeoPackage layer was already built for
  exactly this kind of ArcGIS-side interpolation; a reproducible R
  (`gstat`/`sf`) cross-check as a secondary, scriptable option
  consistent with this project's "everything reproducible" bias; QGIS
  flagged as a free alternative if ArcGIS licensing is ever a
  constraint.
- **Should it be informed by Leapfrog?** Not directly (Leapfrog isn't
  a 2D interpolation tool) — but its 3D zonation (once real lithology
  exists) should determine *which wells get kriged together* (only
  wells screened in the same hydrostratigraphic unit), i.e. Leapfrog
  informs the grouping/masking step that has to happen before any 2D
  surface is computed, not the interpolation itself.
